## What it does

`decomp-spec-gen` groups a decomp project's inventory of functions into **units** and writes one spec per unit to `units/<unit>.md`. Each spec names the unit's source file and address range, the evidence for its boundaries, its success test, the in-scope functions with their size tiers, and the excluded functions with the evidence for excluding them.

A unit is a best-guess original source file, not a feature or a slice of work. The original compiler emitted a run of functions, in address order, from one file, and that order affects the bytes, so the boundaries are a fact to recover from the binary rather than a design to choose. The skill moves a boundary only on evidence and writes that evidence into the unit, and a guess stays labelled as a guess.

## When to reach for it

Type `/decomp-spec-gen`, or the agent reaches for it automatically when a task fits. Usually you never type it: `/decomp-start` calls it once the inventory is checked.

Reach for it when a decomp inventory needs unit specs, or when unit boundaries need revising. For a spec of a feature you have just discussed, use [spec-gen](./spec-gen.md) instead.

| | `decomp-spec-gen` | [spec-gen](./spec-gen.md) |
| --- | --- | --- |
| Input | `inventory.json`, read from the target binary | The conversation, codebase, and glossary |
| Output | One file per unit under `units/`, written by the project tool | One spec issue on your tracker |
| What a spec records | What to reproduce byte for byte, and the success test | Decisions made about what to build |
| Started by | `decomp-start`, or the agent when units need revising | You, typing `/spec-gen` |

## Prerequisites

A decomp project set up by [decomp-setup](./decomp-setup.md), with `inventory.json` written by the project tool's `inventory` command. The specs themselves are generated by `python tools/decomp.py gen-specs`; the skill's own work is the boundary evidence.

## Boundaries from evidence

The `inventory` adapter proposes units. The skill strengthens them with evidence the adapter may have missed, strongest first:

1. Debug information or symbols that name source files.
2. Assert, log, or `__FILE__` strings that name a source file, and the functions that reference them.
3. Runs of functions sharing the same data, strings, or class (RTTI names, one vtable's methods).
4. Alignment gaps and changes in padding style between runs.

Every unit ends up with an `evidence` value, and no function belongs to two units. The success test each spec states is the same everywhere: every ticket in the unit reaches `matched` through the project tool, with the functions in the contract's order in the source file.

## Common questions

**Can I change unit boundaries after tickets exist?**

Yes, and statuses and notes survive the regeneration. Two caveats. The units live in `inventory.json`, which the `decomp-start` tag freezes, so after that tag a boundary change is a change to a frozen path: it goes on a `c/<slug>` candidate branch and through the change flow in the decomp layout, and the tag moves only after a candidate revalidation and your go-ahead. And a ticket id carries its unit (`u0001-00401000`), so a function moved to another unit gets a new ticket under its new id; [decomp-ticket-gen](./decomp-ticket-gen.md)'s count check is what catches the leftover.

**It used to be in `in-progress/`. Where is it now?**

`engineering/`. It graduated with the rest of the decomp skills and now ships in the plugin. Its behaviour did not change on the move.

## It's working if

- Every file under `units/` has an evidence line that says where its boundaries came from, or says plainly that they are a guess.
- No function appears in two unit specs.
- Excluded functions appear in their unit's spec with evidence a reader can check, not silently missing.
- Boundaries line up with source file names the binary itself carries, where it carries any.

## Where it fits

`decomp-spec-gen` is a chain step inside [decomp-start](./decomp-start.md):

```txt
decomp-setup → decomp-start (inventory → decomp-spec-gen → decomp-ticket-gen) → decomp-run
```

It runs after the inventory is checked and before [decomp-ticket-gen](./decomp-ticket-gen.md), which writes one ticket per in-scope function into the units it settled. Its vocabulary (units, tiers, scope) comes from [decomp-standards](./decomp-standards.md). When you are unsure which skill fits, [skill-map](./skill-map.md) routes you.
